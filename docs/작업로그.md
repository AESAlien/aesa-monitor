# 작업로그: aesa-monitor (모니터 개편 + 녹화·로그 분석)

## 모니터 화면 개편과 로그 분석 기능 추가 (2026-11-12)

**진행 내용**
- 위치: `sampleTest/aesa-monitor` (aesa-processor 밖, git 관리 안 함). 바탕은 `aesa-processor/tools/monitor`의 미커밋 개편본(feature/126).
- 패키지 이름을 `aesa_monitor`로 바꾸고 core(계산, tkinter 없음) / io(접속·녹화·재생·로그) / ui(화면)로 나눴다.
- 화면
  - 탭: 빔 / 추적 / 통신 / 분석. 이전 '타겟' 탭과 '추적' 탭은 '추적' 하나로 합쳤다.
  - 모든 탭 맨 위에 판정 한 줄(정상·주의·이상·대기)과 질문을 둔다. 판정 기준은 `core/verdict.py`.
  - 글꼴은 이름 붙은 글꼴로 바꿔 기본 12pt, `A+`/`A−`·Ctrl +/-로 전체 크기를 바꾼다. 종료할 때 monitor.env에 저장.
  - 캔버스 글자는 LabelPlacer로 겹치면 다른 자리에 놓거나 생략한다. 빔 단면은 이름을 범례로 뺐다.
  - 긴 설명은 `?` 버튼(도움말 창)으로 옮겼다.
  - 빔 지도에 추적 영역(안테나 ±60°, -10~60°, yaw만 반영한 근사)과 트랙 위치를 표시한다. 탐색 칸은 격자 간격 크기로 그린다.
  - 색: 탐색 파랑, 확인 노랑, 추적 초록(sim_gui와 같게).
- 녹화: `monitor.aesarec`(받은 프레임 그대로 + 수신 시각). 세션 폴더 `~/aesa-records/<시각>/`.
- 재생: 재생 바(재생/정지, ±5초, 속도, 위치). 같은 탭 코드로 그린다. 재생 중에도 실시간 수신·녹화는 계속.
- 로그 가져오기: `io/log_fetch.py`(local 복사 / ssh scp). 버튼은 이 코드를 백그라운드로 실행. 명령줄 실행 가능.
- 분석 탭: 통계 요약(빔 간격, 탐색 한 바퀴, 탐색→확인, 추적 주기, 확인→트랙, 미탐, 수명, 빔-탐지 차이, 통신, 처리부 로그 이벤트 수),
  분포 그래프, 트랙별 요약, 처리부 이벤트 타임라인(누르면 재생 위치를 이벤트 1초 전으로 옮기고, 거부 이벤트면 그 트랙을 고름).
- `tools/fake_processor.py`: 시험용 가짜 처리부. 모니터 스트림과 처리부 형식 로그(adp_*.log, adp_detection_*.csv)를 만든다.
- 테스트 75개(기존 40 + 신규 35). 클라우드에서 C++ 헤더 대조 포함 전부 통과.

**확인한 것**
- 클라우드(Xvfb)에서 가짜 처리부로 실시간 4개 탭, 녹화, 로그 가져오기(local), 세션 열기, 재생, 이벤트 클릭 이동, 글자 크기 14pt를 화면 캡처로 확인.
- `--stats`로 통계 출력 확인. 녹화 10초(처리부 시각 92초) 통계 계산 0.5초.

**확인하지 못한 것**
- 실제 처리부(aesa-processor)와 실제 모의기(zynq_sim / TargetSIM) 연동 화면.
- ssh 가져오기의 실제 보드 동작(scp 명령 구성과 오류 메시지만 단위 테스트).
- 사용자 PC(호스트)의 Python·tkinter 버전에서 실행. 사용자 VM에는 tkinter가 없다.
- Python 3.8에서의 실행(3.10~3.13에서만 확인).

**이슈 / 결정**
- 메시지 로그(UTC 벽시계)와 처리부 시각 맞추기: main의 "Six worker threads started" 줄을 처리부 시각 0으로 둔다(수 ms 오차, 추정).
- 처리부 로그만 있으면 빔 방향·트랙 목록이 없어 재생은 안 되고, 통계는 탐지 CSV로 일부만 계산한다.
- ssh는 BatchMode라 비밀번호 입력이 안 된다. 보드에 공개키 등록이 필요하다.
- 판정 경계값(±10%, 20/100 ms 등)은 모니터에서 정한 값이다. 처리부 요구사항이 아니다.
- 처리부 내부값(예측 거리, 공분산, NDS)은 여전히 받지 않으므로 연관·차이는 추정이다. 멘토 회의 결과에 따라 별도 메시지로 받으면 정확해진다.

## 빔 지도의 탐색 빔을 원형 빔 범위로 표시 (2026-11-12)

**진행 내용**
- 빔 탭 지도에서 탐색 격자 사각형을 실제 빔 범위 원(지름 = 빔 폭 6°)으로 바꿨다. 189개 원을 옅은 테두리와 중심점으로 모두 그리고, 최근에 쏜 빔은 잔상으로 채운다. 마지막 탐색 빔은 굵은 검은 원.
- 방위·고각을 같은 축척(1°당 같은 픽셀)으로 바꿔 화면에서도 원으로 보이게 했다. 남는 쪽은 범위를 넓혀 가운데 둔다.
- 범례와 도움말(?)에 원의 의미를 적었다.

**근거 / 한계**
- 모의기는 (2Δaz/폭)² + (2Δel/폭)² ≤ 1(cos(고각) 보정 없음)로 빔 안을 판정하므로, 같은 축척의 방위-고각 평면에서는 원 안이 탐지 범위다(TargetSIM_동작분석 4절).
- 빔 폭(6°)이 격자 간격(4.2°, 4.4°)보다 넓어 원이 겹친다. 실제 안테나 빔 모양(빔 패턴)은 반영하지 않는다.
- 클라우드에서 가짜 처리부로 화면만 확인. 사용자 PC 화면은 미확인.

**영향 / 이슈**

- 캡처는 모니터 PC가 다른 장비 사이 패킷을 볼 수 있어야 한다(포트 미러링·허브·보드 tcpdump 중 확인 필요).

## 통신 캡처 출처 구현 (2026-11-12)

**진행 내용**
- 데이터 출처 선택: `MONITOR_SOURCE=copy|capture`, `--source`, `--capture-command`. `io/connection.create_source()`가 복사본 수신(ProcessorConnection) 또는 통신 캡처(CaptureSource)를 만든다.
- 프로토콜: 0xCA01(운용 명령), 0xBA02(모의기 자세), 0xAC03(트랙 삭제) 해석. `MessageFramer(resync=True)`는 잘못된 헤더면 1바이트씩 버리며 다음 경계를 찾는다.
- 이벤트·상태: `ConnectionChanged.source`, `PeerLinkChanged`. `state.peer_connected()`, `state.paused()`는 0xAD01이 있으면 그것을, 없으면 캡처한 TCP 연결·운용 명령을 쓴다. 상단 바·통신 탭·판정이 이것을 쓴다.
- `io/pcap.py`(pcap·pcapng 읽기), `core/capture.py`(IPv4/TCP 추출, 방향별 seq 재조립, 상대 판정, 모니터 복사본 연결 제외), `io/capture.py`(캡처 명령 실행, 캡처 파일 → 녹화).
- 녹화: 메타 `source`, 레코드 종류 4(상대 연결). `--open`으로 pcap/pcapng를 재생·분석.
- `tools/fake_processor.py --peers`: 가짜 모의기·운용통제기가 처리부에 접속해 실제 방향으로 주고받는다.
- 기본 캡처 명령에 `--immediate-mode`를 넣었다(아래 측정).
- 테스트 75 → 95개.

**확인한 것**
- 클라우드(root)에서 `--peers` + 캡처: 연결 도중 시작해도 경계를 다시 찾음. 빔·탐지 100/s, 화면 3개 탭 정상. 복사본 모니터와 동시에 띄워도 중복 없음.
- 저장한 pcap 8000패킷 분석: 놓친 구간 0, 건너뛴 바이트 0, 모니터 연결 1개 제외.
- 처리부 시각 비교(1초 간격): `--immediate-mode` 없으면 캡처가 40~120 ms 늦고, 있으면 20~30 ms 빠름.
- 사용자 PC에서 실행해 `--immediate-mode`가 낫다는 것을 사용자가 확인.

**한계 / 남은 일**
- 실제 장비 사이 캡처(포트 미러링, 보드 ssh tcpdump)는 미확인. 보드 tcpdump 버전·옵션 지원도 모름.
- 캡처를 늦게 시작하면 한 번만 오는 0xAC02·0xCA01을 못 본다(추적 영역 미표시, 운용 상태 '?').
- 캡처 모드에는 처리부 배율이 없어 통신 탭 기대 속도가 배율 1 기준이다(`--speed 2`면 기대 100/s, 실제 200/s).
- 4단계(두 출처 동시 녹화와 비교 통계)는 아직.

## 멘토 회의(261112) 피드백 반영: 용어 2개, 탐색 프레임별 점유율 그래프 (2026-11-12)

**진행 내용**
- "탐색 한 바퀴" → "탐색 프레임 시간"으로 바꿨다(빔 탭 카드·도움말, 판정 문구, 분석 통계 항목, README, 테스트).
  계산은 그대로다(같은 탐색 칸을 다시 방문한 간격 = 탐색 격자 전체를 한 번 도는 시간).
- "RMS" 표기를 없앴다. 추적 탭 "차이 RMS" → "차이 평균", 분석 탭 트랙별 "RMS" → "차이 평균",
  `--stats` 출력 "RMS(m)" → "차이평균(m)", 통계 항목 값 "RMS x m" → "평균 x m".
  - 근거(멘토): 이 값은 측정치(탐지)와 추정치(예측 빔 방향)의 차이다. 둘 다 오차가 있으므로 RMS(E)라고 부르면
    참값 대비 오차로 오해된다. RMSE는 참값을 아는 M&S 사후 분석에서 쓴다.
  - 계산도 제곱평균제곱근에서 산술평균으로 바꿨다. 필드 이름 `rms_angle_error_m` → `mean_angle_error_m`.
  - 판정 경계(게이트 하한의 0.8배/1.5배)는 그대로 두었다. 평균이 RMS보다 작게 나오므로 이전보다 조금 덜 엄격하다.
- 탐색 프레임별 빔 점유율 그래프를 추가했다.
  - `core/frames.py`: `FrameCounter`가 빔을 받아 탐색 프레임마다 탐색·확인·추적 빔 수를 센다.
    탐색 빔 번호가 앞 탐색 빔보다 작아지면 새 프레임으로 본다(처리부 `SearchGrid::nextBeam()`이 0번부터 순서대로 돈다).
  - 완료 프레임 = 탐색 빔 0번에서 시작해 격자 끝 번호까지 가고 다음 0번으로 닫힌 프레임. 모니터를 켠 직후 잘린 프레임,
    격자 재생성(자세 재설정 등)·처리부 재시작으로 끊긴 프레임은 그리지 않고 그 자리에서 선을 끊는다.
  - 빔 탭: 오른쪽 '트랙별 요청 빔 일정'(표 높이 8 → 5행) 아래에 꺾은선(가로 프레임 번호, 세로 %). 최근 2000프레임(약 1시간) 보관.
  - 분석 탭: 통계에 '탐색 프레임별 점유율' 항목 추가. 이 항목이나 '빔 점유율'을 누르면 분포 대신 이 그래프를 그린다.
  - 분석 탭 아래쪽 그래프가 낮은 창에서 잘리던 문제: 그래프·설명을 먼저 아래에 붙여, 공간이 모자라면 통계 표가 줄어들게 했다.
- 테스트 95 → 101개(`tests/test_frames.py` 6개 추가).

**확인한 것**
- 사용자 VM: 101개 중 99개 통과. 실패 2개는 C++ 헤더 대조(`StructSizeTest`)로, aesa-processor가
  `fix/126-unanswered-track-cleanup` 브랜치라 `ST_MonitorStatusMsg`가 없어서다(이번 변경과 무관).
  `feature/126-monitor-program`의 `src/comm`을 `AESA_PROCESSOR_DIR`로 주면 101개 모두 통과.
- 클라우드(Xvfb, Python 3.12)에서 가짜 처리부(×3)로 빔 탭 그래프, 녹화 후 분석 탭 그래프, `--stats` 출력을 화면으로 확인.

**확인하지 못한 것**
- 실제 처리부·모의기 연동 화면, 사용자 PC 화면.
- 확인 빔이 많은 상황(가짜 처리부는 트랙 3~4개라 탐색 약 97%로 거의 평평함).

- `apply_theme(root)`: ttk 테마를 clam으로 바꾸고 탭·버튼·표·콤보박스·입력칸·체크/라디오·스크롤바·슬라이더에 색을 입힌다.
  기본(default) 테마는 탭·버튼 색 지정을 일부 무시해서다. `Fonts`보다 먼저 불러야 한다(theme_use가 앞 설정을 지움).

**이슈와 해결**
- CI 회색은 흰 바탕 대비 약 1.9:1이라 글자색으로 못 쓴다 → 테두리에만 쓰고, 보조 글자는 따로 진한 회색(대비 약 6:1).
- clam 테마는 선택된 탭의 padding을 줄여서 선택 탭만 좁아졌다 → `Fonts.apply`에서 `style.map(padding)`으로 같은 값을 준다.
- 표에서 행을 고르면 글자색이 고정색으로 바뀌어 상태 색(초록·주황·빨강)이 사라졌다 →
  Treeview foreground 맵을 비우고, 고른 행 바탕만 옅은 파랑으로 둔다. 진한 파랑 바탕은 상태 색 글자가 안 읽혀서 쓰지 않았다.
- CI 파랑과 탐색 빔(#378add)은 같은 파랑 계열이지만 명도 대비 약 3.2:1이라 구분된다. CI 파랑은 캔버스 안에 쓰지 않는다.
