## 1. 추적 탭 개편 (방향 결정, 코드 미반영)

### 결정된 것
- 왼쪽 위치 그림을 **부채꼴 전시기(PPI)** 로 바꾼다. 섹터(레이더 정면 위, ±70°)를 기본, 360°(북쪽 위)는 전환 버튼.
  - 표시: 거리 고리, 방위 눈금, 추적 영역(yaw ±60° 점선), 탐색(6°)·확인(3°)·추적(3°) 빔 부채꼴(최근일수록 진함),
    트랙 위치·꼬리·60초 속도 벡터, `#ID 거리·속력`. 고각은 표현하지 않는다(빔 탭 지도에서 봄).
- 오른쪽은 **실시간 감시** 기준으로 구성한다(시안 v5). 이유: ①②③ 카드의 '차이'는 예측(추정)과 측정(잡음 포함)의 차이,
  '연관 탐지'는 모니터가 처리부 판단을 흉내 낸 추정이라, 실시간 판단에 쓰면 추정에 추정을 비교하는 셈이다.
  - 위: **트랙별 상태 줄 (사실 값만)** — 최근 결과 점열(● 갱신 × 미탐 ■ 종료), 연속 미탐 n/한도, 빔 안 위치(막대, 1 넘으면 빨강),
    마지막 갱신 뒤 지난 시간. 행을 누르면 트랙 선택.
  - 아래: 고른 트랙의 **잔차(예측-측정)** 와 **빔 안 위치** 추이(최근 60사이클). 잔차에는 게이트 하한 점선, 빔 안 위치에는 1.0 선.
    제목·도움말에 "참값 대비 오차가 아님"을 밝힌다.
  - **사이클 상세(①예측 ②관측·연관 ③결과, 빔 단면)** 는 접어 둔다(사후 분석용).
- 왼쪽:오른쪽 = 3:2 (1:1이면 1366에서 오른쪽 글자가 잘림, 2:3이면 부채꼴이 작음).

### 정해야 할 것
1. 빔 안 위치 **주의 기준**: 지금은 1 초과(빔 밖)만 빨강. 조기 경보로 쓰려면 주의 경계(예: 0.7)가 필요한데 근거 값이 없다.
   모의기 빔 모델(`(2Δaz/폭)² + (2Δel/폭)² ≤ 1`)과 실제 연동 데이터로 정한다.
2. 잔차 그래프 세로축: 트랙 시작 직후 큰 잔차(가짜 처리부에서 약 130 m)가 축을 키워 이후 변화가 작게 보인다.
   위쪽을 게이트 하한의 n배로 고정할지, 처음 몇 사이클을 뺄지.
3. 사이클 상세를 어디서 펼칠지: 같은 칸 안에서 펼치기 / 별도 창 / 분석 탭으로 옮기기.
4. 지금 트랙 목록 표(수명, 갱신/미탐 수, 차이 평균)가 없어진다. 실시간에 필요하면 상태 줄에 열을 더한다(분석 탭 트랙별 요약에는 있음).
5. 판정 표시 일관성: 빔 탭은 판정 배지 + 카드 줄(`VerdictCardRow`), 추적·통신 탭은 판정 줄(`VerdictBar`).
   추적 탭을 바꿀 때 배지 모양을 맞출지.

### 구현 메모
- 시안 코드: `Claude outputs/next/track_tab_v5_mock.py` (현재 코드 기준 `ui/track_tab.py`를 통째로 바꾼 시안. 사이클 상세 버튼은 동작 없음)
- 시안 그림: `Claude outputs/monitor_redesign_v5_track_monitoring.png`(v5), `monitor_redesign_3_track_ppi_full.png`(섹터/360°),
  `monitor_redesign_v2_2_track.png`(①②③ 한 줄 띠 + 큰 단면, 사이클 상세를 펼칠 때 참고)
- 부채꼴 그리기 요점
  - Tk 호 각도는 동쪽 0°·반시계라 `start = 90 − (방위 − 회전 + 폭/2)`. 섹터 보기는 회전 = yaw, 360°는 0.
  - 섹터 반경은 대부분 칸 너비가 정한다: `min(높이 − 30, (너비/2 − 30) / sin 70°)`.
  - 탐색 빔 잔상은 50 ms만(10 ms마다 약 4°씩 움직여 길게 두면 넓은 부채꼴이 화면을 덮음).
  - 속도 벡터 방향도 같은 회전을 적용(`heading − 회전`).
  - 상태 줄 결과 점 개수는 칸 너비에 맞춰 줄인다(1366에서 약 12개).
- 테스트: 화면 코드는 단위 테스트가 없다. 상태 줄 값 계산(최근 결과, 마지막 갱신 경과)을 core 쪽 함수로 빼면 테스트를 붙일 수 있다.

## 2. 문제 자동 기록 후속 (`core/problems.py`)

- **실제 데이터로 검증**: 가짜 처리부에서는 미탐·트랙 종료·빠진 빔·연결 끊김·재시작만 확인했다. 실제 연동에서
  - 탐색 프레임 시간·추적 주기가 트랙 생성·삭제 순간 잠깐 기준을 벗어나 문제가 너무 많이 잡히는지
  - 확인 실패(오경보)가 잦아 목록을 덮는지 → 수준을 낮추거나 기본 거르기에서 뺄지
  - 묶는 시간(`MERGE_MS` 2초)이 맞는지
- **빔 안 위치 조기 경보**: '빔 밖 탐지'는 모니터 연관 추정에 기대 자동 기록에서 뺐다(PR 리뷰). 빔 안 위치는 추적 탭 상태 줄에서
  보는 값으로 쓰고, 주의 기준은 1장 '정해야 할 것' 1번에서 정한다. 자동 기록에 다시 넣으려면 연관과 무관한 조건이어야 한다.
- **처리부 로그 문제의 녹화 위치**: 로그는 처리부 시각만 있어, 로그 실행 수 = 녹화 구간 수일 때만 순서대로 짝짓는다(추정).
  로그 파일 이름의 실행 시각(벽시계)과 녹화의 수신 시각으로 맞추면 정확해질 것으로 추측.
- **이벤트 타임라인 구간 분리**: 처리부 시각 축이라 처리부 실행이 여럿이면 겹쳐 그려진다(목록·이동은 녹화 위치라 정확).
  고른 처리부 실행 구간만 그리거나 구간별로 나눠 그린다.
- **분석 탭 트랙별 요약**: 처리부 실행 구간이 여럿이면 같은 트랙 ID가 반복된다. 구간 표시(`[실행 n]`)가 필요.
- **긴 녹화 성능**: 40초 녹화 0.2초 → 10분 약 3초(추정). 수십 분이면 여는 시간이 길어지므로 백그라운드 계산이나 진행 표시 검토.
- **통계 요약 연계**: 통계 표에 '자동 기록 문제' 항목(종류별 건수)을 더할지.
- **실시간 기록 보존**: 지금 실시간 문제는 메모리에만 있고, 녹화를 열면 다시 계산한다. 녹화하지 않은 구간의 문제를
  목록으로라도 남길지(파일 저장) 검토.
