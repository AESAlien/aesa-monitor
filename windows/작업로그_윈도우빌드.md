### 진행 내용
- 코드 최신 여부: 로컬 `main` = `a77d1f8`, GitHub `AESAlien/aesa-monitor` 원격 `main`도 `a77d1f8`로 같음.

  - 노트북 환경: Python 3.14.6, PyInstaller(빌드 때 설치), Wireshark 4.6.8 dumpcap, Npcap 1.88.
- `windows/dist/monitor.env`: 처리부 주소 `MONITOR_SERVER=192.168.10.20:3200`(README 기본값, 확인 필요),
  캡처 인터페이스 `이더넷 2`(Realtek, `\Device\NPF_{92DAE06A-C50E-4EEB-8A17-0ACBBB9A1934}`).
- 실행 확인
  - exe 실행 → 화면 정상, 한글 정상(맑은 고딕), dumpcap 콘솔 창 안 뜸, 캡처 연결됨.
    `이더넷 2` 케이블이 빠져 있어 받은 패킷은 0.
  - `loopback_test.bat`(가짜 처리부 `tools/fake_processor.py --peers` + 루프백 캡처):
    처리부·운용통제기·모의기 모두 연결, 빔 명령·탐지 108/s, 트랙 4개, 마지막 수신 0.1 s 전.

### 이슈와 해결
| 이슈 | 원인 | 해결 (windows/aesa_monitor_win.py) |
| --- | --- | --- |
| onefile exe에서 monitor.env를 못 찾고 저장 값이 사라짐 | `settings.py`가 `__file__` 기준 폴더를 씀 → 임시 폴더 | 설정 경로를 exe 폴더로 바꿈 |
| 캡처 명령의 Windows 경로가 깨짐 | `shlex.split`(POSIX)가 역슬래시를 지움 | Windows에서는 명령 문자열을 그대로 CreateProcess에 넘김 |
| dumpcap·ssh 실행 때 콘솔 창이 뜰 수 있음 | 창 없는 exe의 자식 프로세스 | `CREATE_NO_WINDOW`, `stdin=DEVNULL` |
| tcpdump 없음 | Windows | Wireshark `dumpcap ... -P -q -w -` 사용, Wireshark 폴더를 PATH에 추가 |
| `UserKnownHostsFile=/dev/null` | Windows에 /dev/null 없음 | monitor.env 템플릿에서 `NUL` |
| 시작 오류가 안 보임 | 창 없는 exe는 stdout/stderr 없음 | `aesa-monitor.log`에 기록 + 메시지 상자 |

### 남은 확인 (추측·미확인)
- "브릿지" 구성: 노트북에 Windows 네트워크 브리지는 없음. 유선 랜카드는 `이더넷 2` 하나.
  VMware VMnet 어댑터가 있어 VM의 브리지 네트워크로 Zynq와 통신하는 구성일 수 있음(추측).
  이 경우 호스트의 `이더넷 2`에서 Npcap이 VM 트래픽을 보는지 실제 연결에서 확인 필요.
- Zynq 실제 주소·포트(현재 192.168.10.20:3200 가정).
- dumpcap 지연: 루프백에서는 '마지막 수신 0.1 s 전' 수준. 실제 보드에서 측정 필요.

## 저장소 정리 (2026-11-18)
- 실행파일은 저장소에 올리지 않는다. exe·중간 파일은 기존 `.gitignore`의 `build/`, `dist/`로 이미 무시됨.
- `.gitignore`에 `*.log`, `windows/check_env.txt` 추가. check_env.txt에는 노트북 IP·MAC과 주변 장비 목록이 들어 있다.
- 커밋 대상으로 남는 것: `windows/` 아래 aesa_monitor_win.py, build.bat, check_env.bat, loopback_test.bat,
  monitor_loopback.env, 이 로그.
- exe 배포는 GitHub Releases 첨부 또는 공유 폴더(exe 옆에 monitor.env 동봉)로 한다.

## 캡처 랜카드 자동 선택·노트북 IP 설정·자동 빌드 배포 (2026-11-18)

### 진행 내용
- **캡처 랜카드 자동 선택** (`windows/aesa_monitor_win.py`)
  - 캡처 명령의 `{interface}`를 처리부 주소(MONITOR_SERVER)와 같은 네트워크 주소를 가진 랜카드의 Npcap 장치(`\Device\NPF_{GUID}`)로 바꾼다.
  - 랜카드 GUID와 IPv4 주소는 PowerShell(`Get-NetIPAddress`, `Get-NetAdapter`)로 읽는다.
  - 처리부가 127.0.0.1이면 `\Device\NPF_Loopback`을 쓴다.
  - 캡처를 다시 시작할 때마다 다시 찾는다. 그래서 노트북 IP를 나중에 넣어도 된다.
  - 못 찾거나 PowerShell이 실패하면 ValueError로 바꾼다. 이 오류는 캡처 실패 사유로 보이고, 캡처 스레드는 계속 다시 시도한다.
  - 처음 만드는 monitor.env 기본값을 `dumpcap -i {interface} ...`로 바꿨다. 이미 GUID를 적은 monitor.env는 그대로 동작한다.
- **노트북 IP 고정** (`windows/setup_network.bat`, `setup_network.ps1`): 관리자 권한으로 유선 랜카드를 고르고 구성을 고른다.
  - 모니터만: .30
  - 1대 구성: .30, .10, .100. .10과 .100은 SkipAsSource로 둔다.
  - DHCP 복원
  - 기존 IPv4 주소와 기본 게이트웨이를 지우고 고정 주소를 넣는다. 재부팅해도 유지된다.
- **자동 빌드·배포** (`.github/workflows/windows-exe.yml`)
  - Linux(ubuntu)에서 단위 시험을 돌린 뒤, Windows에서 `build.bat`으로 exe를 만든다.
  - zip 구성: exe, 처리부 `.env.example`→`.env`, setup_network, README.txt
  - main 반영이나 수동 실행 때는 Actions artifact로 올린다. `v*` 태그를 올리면 Releases에도 붙인다.
  - 단위 시험을 Linux에서 돌리는 이유: 일부 시험(`test_log_fetch`의 scp 경로 등)이 POSIX 경로를 전제로 한다.
- `windows/build.bat`: 미리 정한 `PY` 환경 변수를 쓰게 했다(CI: `PY=python`).
- `windows/README.txt`: 배포 zip용 설명.
- `.gitattributes`: `*.ps1`을 CRLF로 둔다.
- 시험: `tests/test_windows_entry.py` 10개(목록 해석, 같은 네트워크 선택, 루프백, 못 찾음 안내, 처리부 주소 제외, 명령 치환, 직접 지정 유지, PowerShell 실패). 전체 159개 통과(Linux, 처리부 폴더가 없으면 2개 건너뜀).

### 확인한 것 / 못 한 것
- 확인: `setup_network.ps1`과 어댑터 조회 명령의 PowerShell 구문(pwsh 7.4 파서), 가짜 cmdlet으로 조회 출력 형식, actionlint 통과.
- 확인: 캡처 소스에 연결했을 때 랜카드 없음, PowerShell 없음, 시간 초과가 실패 사유 문구로 보이는 것.
- 못 함: 실제 Windows에서 setup_network 실행(네트워크 설정 변경), PowerShell 조회, Actions 실제 실행.
- 못 함: 클라우드 Wine이 이번에는 실행되지 않아 exe 재빌드를 확인하지 못했다. 빌드 방식은 이전과 같다.
